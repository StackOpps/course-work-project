Chapter 3: Methodology

3.1 System Overview

This paper takes an experimental, implementation-based approach, using AWS-native services to design, build and evaluate a disaster recovery solution aimed specifically at small businesses. The decision not to rely on surveys or purely theoretical analysis comes directly from the gap identified in Chapter 2. Most of the existing literature treats disaster recovery either conceptually or within complex environments such as Kubernetes or hybrid cloud setups (Bhavsar et al., 2023; Kim, Choi and Jung, 2024; Bahaweres and Najib, 2023). What is missing is a practical evaluation of a simple, AWS-native solution that a small organisation with limited budget and technical staff could realistically adopt.

The research is quantitative in nature. A representative small-company workload is deployed on AWS and managed entirely through Infrastructure as Code, with a backup and recovery architecture built around it. Rather than staging failures and restores manually, detection and recovery are driven by a real, externally-evaluated health signal: an Amazon Route 53 health check probes the live storefront from outside any single AWS region, and a CloudWatch alarm on that signal starts the recovery workflow automatically once the site has failed a sustained run of consecutive checks. This produces measurable results across RTO, RPO, restore success rate, automation level and cost rather than descriptive comparison alone, as was largely the case in the reviewed literature. Every automated drill, and every result from AWS Backup's own restore-testing feature, is written to a version-controlled history file and rendered on a small public dashboard, so results accumulate as repeatable, timestamped evidence rather than one-off manual measurements.

The overall design sits deliberately between the two extremes discussed in Chapter 2. On one side is manual backup and restore, which is cheap but slow and prone to human error. On the other is hot standby or active-active recovery, which is fast but expensive and often more than a small business needs. This project tries to find a workable middle ground: automated enough to reduce delay and risk, but without the ongoing cost of infrastructure that sits idle most of the time — the DR region holds only a backup vault and copied recovery points during normal operation, not a standing copy of the application. All components are provisioned and managed through Terraform, split into three independently deployable stacks — the application environment, the cross-region backup and failure-detection stack, and an AWS Backup restore-testing stack — with GitHub Actions handling provisioning, scheduled backup verification, and the recovery workflow itself, so that the whole setup reflects something a small team could genuinely maintain, rather than a one-off academic exercise.

3.2 System Components

To keep the implementation grounded rather than abstract, this paper is built around a fictional small e-commerce vendor called CraftHaven, which sells handmade home and lifestyle products through its own online store. CraftHaven is a reasonable stand-in for the kind of organisation this research is aimed at: a small team of under ten people, no dedicated infrastructure engineer, no existing disaster recovery plan, and a business that is entirely dependent on its website and order data to function. If the site goes down or order data is lost, there's no fallback, which is exactly the kind of risk this dissertation is trying to address.

The system is made up of the following components:

Application layer
CraftHaven's web application runs on an Amazon EC2 instance behind an Application Load Balancer, serving the storefront over HTTPS via an ACM certificate (HTTP requests are redirected to HTTPS at the load balancer). Customer records and order history are stored in an Amazon RDS (MySQL) database, while product images and other static assets sit in Amazon S3. Everything runs inside an Amazon VPC, with the web tier and database tier separated across public and private subnets, and the web instance reachable only from the load balancer's security group. Administrative access to the instance uses AWS Systems Manager Session Manager rather than SSH keys or a bastion host, removing key-management overhead that a team with no dedicated infrastructure engineer would otherwise carry.

Backup layer
AWS Backup runs an hourly backup plan against every resource tagged Backup=true — currently the RDS instance, the only tier holding data that cannot be reproduced from the repository itself. The EC2 instance and the S3 site content deliberately sit outside this tag-based selection: the EC2 instance is stateless, since its boot process reinstalls the web server and re-syncs content from S3 on every launch, and the S3 objects are themselves Terraform-managed and re-uploaded on every apply. Recovery for those two tiers is therefore Infrastructure-as-Code reproduction rather than a restore from a recovery point; AWS Backup's role is scoped to the one tier that genuinely needs it. Each RDS recovery point is copied automatically to a second backup vault in a separate DR region (eu-west-1) as soon as it is created, so a restore never depends on the primary region (eu-west-2) being healthy.

Protection layer
AWS Backup Vault Lock (governance mode, with configurable minimum and maximum retention) is implemented in Terraform for both the primary and DR vaults, but it is not currently enabled in the deployed environment. Because the environment is a research testbed rather than a persistent production deployment, it is torn down on a short recurring schedule to bound AWS cost, which requires its vaults' recovery points to be deletable on demand; a locked vault would block that teardown until the minimum retention period elapsed. Vault Lock is therefore a configuration capability available in the codebase rather than an active, verified control in the running system — a limitation carried into the evaluation in Section 3.4.

Recovery layer
Recovery is not a separate restore script but a re-application of the same Terraform configuration that provisions the primary environment, run against the DR region under its own state, and parameterised with the ARN of the latest RDS recovery point in the DR vault so the database instance restores from real data instead of coming up empty. The EC2 instance and S3 content rebuild themselves as a side effect of that same apply, for the reasons set out under Backup layer above. This is the core idea behind the whole project: recovery reuses the exact code that built the primary environment rather than a separate, hand-maintained recovery procedure.

Failure detection and failover layer
Failure detection relies on a single, externally-evaluated signal: an Amazon Route 53 health check makes HTTPS requests against the live storefront from AWS's own distributed network of checkers, outside any single AWS region's control plane. Its status metric is published to CloudWatch only in us-east-1 — an AWS platform constraint, not a design choice — so the alarm watching it, and the automation it triggers, deliberately live in a third region, separate from both the primary and DR regions. This means detection keeps working even if the primary region's own monitoring and event infrastructure is itself impaired. The health check requires three consecutive failed probes before it reports unhealthy, and the CloudWatch alarm watching that status requires three further evaluation periods in breach before it fires, so a single transient failure does not trigger recovery while a genuine outage is still caught within a few minutes. Once the alarm is in ALARM state, an EventBridge rule calls the GitHub REST API's repository_dispatch endpoint through an API destination, starting the recovery workflow with no human needing to notice the outage first. Route 53 remains the public DNS entry point throughout; the workflow repoints it at the DR load balancer once the rebuilt environment passes a smoke check.

Monitoring layer
Amazon CloudWatch tracks EC2 status checks, RDS free storage, and AWS Backup job/copy/restore state changes in both the primary and DR regions, alerting a per-region SNS topic. AWS CloudTrail runs a single multi-region trail that logs backup, restore, and configuration changes, giving a clear audit trail if something needs investigating later.

Infrastructure as Code and automation layer
The environment is split into three independent Terraform root modules sharing one S3 backend under separate state keys, with locking handled by Terraform's native S3 lock file rather than a separate DynamoDB table: the application environment, the primary/DR backup vaults and failure-detection stack, and AWS Backup's restore-testing plan. A single reusable GitHub Actions workflow runs terraform fmt, validate and plan against whichever module is targeted, and applies or destroys it on demand. One workflow provisions all three stacks on manual dispatch, another plans the application stack's Terraform on every pull request, and a scheduled workflow tears the whole environment down on a short recurring cycle to bound AWS cost — emptying both backup vaults of recovery points first, since AWS Backup refuses to delete a vault that still holds any.

The advantage of this setup is that it's not just the data that can be recovered — the infrastructure itself is disposable and rebuildable, which matters a lot for a small company that can't afford to have someone rebuild servers by hand under pressure.

3.3 Architecture Design

The architecture follows a straightforward flow, with Terraform and GitHub Actions acting as the glue between provisioning, backup, and recovery.

Provisioning. Each of the three Terraform stacks is stored in GitHub and applied independently through the same reusable workflow: the application environment, the backup/detection stack, and the restore-testing stack. A manually dispatched workflow run provisions any combination of the three; a pull-request workflow plans the application stack's changes without applying them.

Normal operation. Route 53 resolves customer requests to the load balancer in the primary region (eu-west-2). The EC2-hosted application serves traffic over HTTPS, writes to RDS, and pulls product images from S3.

Automated backup. AWS Backup runs hourly, creating recovery points for the RDS instance and copying each one immediately to a second, locked-in-code vault in the DR region (eu-west-1), so restores never depend on the health of the primary region.

Monitoring. CloudWatch keeps an eye on EC2/RDS health and AWS Backup job status throughout, while CloudTrail logs every backup, restore, and infrastructure change in the background.

Failure detection. The system does not wait for customers to report a broken site. A Route 53 health check probes the storefront from outside AWS every 30 seconds; after three consecutive failed probes it reports unhealthy, and a CloudWatch alarm on that status — evaluated in us-east-1, deliberately outside both the primary and DR regions — must stay in breach across several evaluation periods before a disaster is declared. This filters out transient blips while still detecting a real outage within a few minutes, even at zero customer traffic.

Recovery. When the alarm fires, an EventBridge rule calls the GitHub Actions recovery workflow through an API destination. No human has to notice the outage first. The workflow looks up the latest RDS recovery point in the DR vault, then re-applies the application stack's Terraform configuration against the DR region under a separate state, passing that recovery point's ARN so RDS restores from real data while everything else provisions from the same code that built the primary region.

Failover. Once the re-provisioned DR environment passes a smoke check, the workflow explicitly updates the Route 53 record to point the domain at it — an imperative step kept outside Terraform state so the primary and DR applies never contend over ownership of the DNS record. From the customer's point of view nothing changes: the same domain simply starts resolving to the DR region.

Validation. The workflow records RTO as the time from a timestamp taken at its own start (the closest available proxy for the alarm firing, since the exact alarm timestamp is not threaded through the dispatch payload) to the DNS cutover, and RPO as that same start timestamp minus the creation time of the RDS recovery point actually restored from. Both are appended automatically to a version-controlled history file and rendered on a small GitHub Pages dashboard, alongside independent results polled from AWS Backup's own restore-testing plan, which restores a sample recovery point on its own hourly, AWS-internal schedule and validates it, decoupled from any live outage. A separate, standalone script also exists for ad hoc, single-resource restore timing outside either automated path, for manual verification during development.

3.4 Evaluation Criteria

The solution is evaluated against a set of criteria that come directly out of the trade-offs discussed in Chapter 2:

| Criterion | Definition | Measurement Method |
|---|---|---|
| Recovery Time Objective (RTO) | Time from failure trigger to full application availability | Measured automatically by the recovery workflow, from a timestamp taken at workflow start (the closest available proxy for the health-check alarm firing) to the Route 53 cutover; recorded to the dashboard history file |
| Recovery Point Objective (RPO) | Data loss window between last successful backup and point of failure | Calculated by the same workflow from the creation timestamp of the RDS recovery point actually restored from, against the failure-trigger timestamp |
| Restore Success Rate | Proportion of restore attempts completing without manual intervention | Measured two ways: full end-to-end recovery drills (triggered automatically or dispatched manually) and AWS Backup's own hourly restore-testing plan against the DR vault, both recorded to the same dashboard |
| Automation Level | How much of backup/restore is manual vs. automated | Read from the GitHub Actions workflow definitions: provisioning, backup, detection, and recovery all run without a manual step once a failure is confirmed; only environment provisioning/teardown and ad hoc restore checks require a human or schedule to initiate |
| Backup Protection | Whether backups are safe from unauthorised deletion or change | Vault Lock is implemented in Terraform for both vaults but disabled in the running environment (Section 3.2); evaluated as a configuration capability rather than a verified running control |
| Monitoring and Auditability | Whether backup/restore actions are visible and logged | Verified via the CloudWatch alarms and EventBridge rules in each region and the multi-region CloudTrail trail |
| Cost | Estimated AWS cost of running the solution | Calculated via AWS Cost Explorer/pricing calculator; bounded in practice by tearing the non-production environment down between test runs rather than leaving it running continuously |
| Infrastructure Reproducibility | Whether the environment can be rebuilt from code alone | Verified directly by the automation used for the evaluation itself: the application stack is destroyed and re-provisioned on a recurring schedule, and every recovery drill re-provisions it from the same code in a second region |

Taken together, these criteria let the solution be judged not just on whether recovery is possible, but on whether it strikes a reasonable balance between speed, reliability, automation, reproducibility, and cost — which is really the central question running through the whole literature review.

3.5 Advantages of the Proposed Solution

A few things stand out as genuine advantages of this approach over the strategies covered in Chapter 2.

It's considerably cheaper to run than hot standby or active-active recovery, since the DR region holds nothing but a backup vault during normal operation rather than duplicate infrastructure sitting idle — while still being faster and more reliable than a purely manual backup-and-restore process. Automating both the backup schedule and the infrastructure provisioning also cuts down heavily on the manual steps and human error that the literature repeatedly flags as a weak point in traditional backup-and-restore setups (Naik, 2016; Alhazmi and Malaiya, 2013).

Because the whole environment is defined in code, CraftHaven's infrastructure becomes something that can itself be rebuilt after a disaster, not just the data sitting on top of it — which is a step beyond most of the approaches discussed earlier, where the assumption tends to be that the underlying infrastructure is already there (Bahaweres and Najib, 2023; Rahman, Mahdavi-Hezaveh and Williams, 2019). Scoping AWS Backup to only the tier that actually holds irreplaceable data, and letting Infrastructure as Code reproduce the rest, keeps that recovery path simple rather than backing up things that Terraform can already rebuild for free. Placing failure detection on an externally-evaluated health check, deliberately outside the regions it protects, also means a real regional outage cannot silently disable the very mechanism meant to detect it. Pairing CloudWatch and CloudTrail into the setup means backup and recovery actions are visible, addressing a point raised in Chapter 2 that recovery failures are often caused less by missing backups and more by nobody noticing something had gone wrong in the first place.

Perhaps most importantly for the audience this research is aimed at, none of this requires a dedicated infrastructure engineer on staff. Routine provisioning, backups and recovery all run through pre-built automation pipelines, which fits well with the reality of small businesses that simply don't have the resources to hire specialised staff for this kind of work (Wowrack, 2024). The main gap against that ambition is Vault Lock: the protection the original design called for is written but switched off in this testbed, and turning it on in a real deployment would mean accepting a fixed minimum retention period the environment could no longer be freely torn down within.
