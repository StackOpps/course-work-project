Chapter 4: Results and Analysis

4.1 Overview

This chapter evaluates the implementation described in Chapter 3 against the criteria set out in Section 3.4, using the evidence the system itself has produced: the drill history recorded in `docs/data/history.json`, the CI/CD workflow definitions that generated it, and the Terraform configuration that defines what is actually running. Where the evidence is thin — and in places it is, since this is a testbed that has been exercised manually rather than run continuously over months — that is stated plainly rather than papered over. A single data point is still a data point; it is just not a trend, and this chapter is careful not to present it as one.

At the time of writing, one full DR failover drill has been recorded through `dr_failover.yml`, and no results from AWS Backup's own restore-testing plan have been recorded yet by `record_restore_testing.yml`. Cost data collection via AWS Cost Explorer (`record_cost.yml`) has been added to the pipeline but had not yet produced its first recorded snapshot at the time of writing. The analysis below works with what actually exists rather than projecting forward.

4.2 Recovery Time Objective

The one recorded drill (triggered 2026-08-07T13:12:47Z against `shop.crafthavens.com`) shows an RTO of 16.29 seconds — the time from the workflow's recorded start to the Route 53 cutover.

That number needs to be treated with suspicion rather than reported as a success. AWS RDS restores from a snapshot routinely take several minutes even for a small instance class, well before EC2, the ALB, or DNS come into play, so a genuine "DR region has nothing running, rebuild it from a recovery point" scenario cannot plausibly complete end-to-end in 16 seconds. The far more likely explanation is that the DR region already had matching infrastructure in place when this particular drill ran — from a prior deploy that had not yet been torn down, or a very recent one — so `terraform apply` converged almost instantly because there was little or nothing left to create. In that case the 16 seconds mostly measures the smoke check and DNS cutover, not a real rebuild.

This matters for how the result should be read: it isn't evidence that CraftHaven recovers in 16 seconds, and treating it that way would misrepresent the system. What it does demonstrate is that the mechanics work — the workflow ran the correct sequence (provision, smoke check, cutover) and returned a value at all, which several months earlier would have required someone to do all of that and time it by hand. What it does not yet demonstrate is a worst-case RTO under conditions that resemble an actual disaster, where the DR region genuinely holds nothing but a backup vault when the drill starts. Section 5.1 returns to what a methodologically sound measurement of this would need to look like.

4.3 Recovery Point Objective

The same drill recorded an RPO of 2,746 seconds — 45 minutes and 46 seconds — measured as the age of the RDS recovery point actually restored from, relative to the drill's start time.

This number is more trustworthy than the RTO, because it isn't sensitive to whatever state the DR region happened to be in; it comes directly from the timestamp AWS Backup attached to the recovery point at creation. It also sits inside the range the design should produce: the backup plan runs hourly with a 180-second completion window (Section 3.2), so the theoretical worst case for RPO is a little over 63 minutes — the gap between one hourly backup finishing just after a failure and the next one not yet having started. 45 minutes 46 seconds falls comfortably inside that bound, which is a genuine, if single-sample, confirmation that the hourly schedule behaves as designed rather than silently drifting or skipping runs.

The obvious limitation is the same one that applies throughout this chapter: one measurement cannot distinguish "RPO is reliably well inside the hourly bound" from "this happened to land in a favourable part of the hour." A meaningful RPO claim needs drills spread across enough points in the backup cycle to show the full range, not just one sample near the middle of it.

4.4 Restore Success Rate

Combining the one full failover drill with AWS Backup's own restore-testing plan gives a restore success rate of 100% (1 of 1) at the time of writing — the dashboard computes this live from `history.json` rather than it being asserted here. It's worth being explicit about what that percentage does and doesn't mean: with a sample size of one, "100%" and "the only attempt so far worked" are the same statement, and the figure will be far more meaningful once `record_restore_testing.yml` has folded in a run of AWS Backup's hourly restore-testing plan, which validates a restore independently of any drill and accumulates evidence without requiring a human to trigger anything.

4.5 Automation Level

This criterion is read from the workflow definitions rather than measured from drill data, and here the design largely does what Chapter 3 claimed. `dr_failover.yml` runs Terraform re-apply, RDS restore lookup, smoke check, and DNS cutover as one unattended sequence once dispatched — the only human step is the dispatch itself, which is a deliberate decision point rather than a gap, given the system has no automated failure detection to trigger it otherwise (Section 4.9 returns to this). `record_restore_testing.yml` and the AWS Backup restore-testing plan it polls run entirely on AWS-managed and repo-scheduled cron, with no human step at all. The place automation is genuinely incomplete is upstream of recovery: provisioning and teardown both still require a workflow_dispatch click, so a small team running this in practice would need someone to notice an outage and start the drill, not just wait for a page.

4.6 Backup Protection

This is the criterion where the implementation changed materially since Chapter 3 was written. AWS Backup Vault Lock is now enabled in Terraform for both the primary and DR vaults (`backup/vault.tf`), with a one-day minimum retention: once a recovery point is created, it cannot be deleted before that day passes, by anyone, including the account root user. The compromise that made this possible without breaking the testbed's cost-bounding teardown is architectural rather than a disabled control — the backup vaults were pulled out of the 2-hourly `destroy.yml` schedule that tears down `infra/`, since AWS Backup refuses to delete a vault holding locked recovery points and repeatedly trying to do so would just fail. The vaults are destroyed only on a manual, opt-in run of `destroy.yml`, once the retention window has actually elapsed.

Two honest caveats belong here. First, a one-day minimum is a testbed-scale compromise, not what a production small-business deployment would choose — a real deployment would likely set this closer to the 7-35 day range common in industry guidance, accepting the higher storage cost of vaults that can't be torn down on a short cycle. Second, this control is defined in Terraform and enabled at the time of writing, but the recorded drill in Section 4.2 predates this change, so no drill result in the current history reflects a run against a Vault-Lock-protected vault; that will only be true of drills recorded from this point forward.

4.7 Monitoring and Auditability

This criterion is verified directly from the deployed configuration rather than from drill data: CloudWatch alarms exist in both regions for EC2 status checks, RDS free storage, and AWS Backup job/copy/restore state changes, each wired to a per-region SNS topic (`backup/monitoring.tf`, `infra/monitoring.tf`), and a single multi-region CloudTrail trail logs backup, restore, and configuration-change events. Nothing about this analysis changes that finding — it remains verified, and there is nothing in the drill history that would confirm or contradict it since it is a structural property of the deployed configuration, not something a drill measures.

4.8 Cost

Cost is now pulled from AWS Cost Explorer daily by `record_cost.yml` and rendered as whole-account spend on the dashboard, rather than only being bounded through infrastructure teardown as it was when Chapter 3 was written. At the time of writing this had not yet produced a recorded figure, since it is a scheduled daily poll rather than something triggered by a drill, so this chapter reports the instrumentation rather than a specific dollar amount it hasn't yet measured — printing a number here that the pipeline hadn't actually produced would be worse than reporting none. What can be said with confidence is the structural cost story from Chapter 3 still holds regardless of the exact figure: the DR region carries no standing compute, only a backup vault, and `infra/` (the EC2/RDS/ALB tier that actually costs money) is torn down every two hours between sessions. Now that Cost Explorer is wired in, the next revision of this chapter — or the dashboard a reader consults directly — can state that bound as a measured number instead of an assumption.

4.9 Discussion

Read together, these results support a narrower claim than "the system meets its design goals," and a more useful one: the automation pipeline itself works end-to-end, and the one real measurement obtained through it (RPO) is consistent with the hourly backup design. The other headline number (RTO) is not yet trustworthy as a worst-case figure, for a reason this chapter can name precisely rather than guess at — a fast re-apply against a DR region that wasn't actually empty. That is a fixable methodological gap, not a flaw in the recovery mechanism itself, and Section 5.1 sets out what a drill needs to control for to produce an RTO number worth citing.

The design's core trade-off argument from Chapter 3 — cheaper and faster than manual restore, cheaper than hot standby, at the cost of a manual trigger and (previously) unenforced backup protection — is better supported now than it was at the point that chapter was written, specifically because Backup Protection moved from "implemented but disabled" to "enabled and running" without giving up the cost-bounding teardown that made the disabled state seem necessary in the first place. That is a genuine result of this work, not just a description of what was built: it shows the trade-off Chapter 3 argued for in the abstract — automation without the ongoing cost of idle standing infrastructure — extends to backup protection as well, once the teardown boundary is drawn around the compute tier rather than the whole environment.
