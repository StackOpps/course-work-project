Chapter 5: Future Work and Conclusion

5.1 Future Work

The items below follow directly from gaps Chapter 4 identified in the running system, rather than being a generic wish list.

Measuring a genuine worst-case RTO. The one recorded RTO (16 seconds, Section 4.2) is almost certainly not a real cold-start measurement, because the DR region likely wasn't actually empty when that drill ran. A methodologically sound version of this drill would destroy the DR-region `infra/` state immediately before triggering `dr_failover.yml`, forcing Terraform to provision genuinely from nothing and RDS to restore for real, rather than converging against infrastructure that was already mostly there. Without that control step, RTO numbers from this pipeline can't be trusted as worst-case figures, only as evidence the automation runs.

A larger drill sample. Every result in Chapter 4 rests on a single drill. RTO, RPO, and restore success rate all need repeated runs — ideally spread across different points in the hourly backup cycle — before a mean, a range, or a percentile means anything. `dr_failover.yml` already writes every run to the same version-controlled history file, so this is a matter of running it repeatedly over time rather than building new tooling.

Closing the last manual step, carefully. Automation level (Section 4.5) is complete from the point of dispatch onward, but dispatch itself is still a human clicking a button. The obvious fix is a CloudWatch composite alarm wired to trigger `dr_failover.yml` via `repository_dispatch`, and that alone would already let RTO be measured from actual failure detection rather than from whenever an operator happened to notice. But a static threshold alarm (EC2 status check failed, RDS free storage below X) is a blunt instrument — it catches the failures the designer thought to name and misses the ones that look like gradual degradation rather than a hard stop. CloudWatch's own anomaly-detection bands, which learn a normal range per metric instead of a fixed threshold, would catch more of that middle ground without a human having to guess the right static number for every alarm up front. This is listed as future work, not something already built — an earlier version of the dashboard text implied a Route 53 health-check trigger already existed, which the workflow definition (`on: workflow_dispatch` only) does not support; that text has been corrected.

Whether that detection should be allowed to trigger failover on its own is a separate question from whether it should exist, and this project's own results argue for caution. A failover isn't free here: it's a cold RDS restore plus a DNS cutover, not an instant swap, and Chapter 4 is honest that the one RTO number on record almost certainly understates what a real cold-start recovery costs. An anomaly detector with a false-positive rate that looked fine in a demo could, in production, trigger that expensive path over a transient blip more often than a human operator would have. A more defensible middle ground — and arguably a better fit for a small business with no on-call engineer to interpret raw metrics — is AI as triage rather than AI as trigger: when an alarm fires, feed the surrounding CloudWatch and CloudTrail context to an LLM and have it produce a plain-English incident summary and a recommendation, and let a human still make the call to dispatch `dr_failover.yml` from that summary instead of from a wall of metric graphs. That keeps the audit story Chapter 4 credits this design with (Section 4.7) intact — a human decision that CloudTrail can log, not a model's internal reasoning that it can't — while doing the part a small business actually lacks the expertise for: telling a signal that matters from one that doesn't. Full autonomy is worth revisiting once the repeated-drill dataset from the item above exists to actually measure a detector's false-positive rate against; deciding to automate the trigger before that evidence exists would be optimising for a demo, not for CraftHaven's actual risk.

Making the accumulating data pull its own weight. Once enough drills exist to plot a real distribution rather than a single point, the more interesting question stops being "what was the last RTO" and becomes "is this run worse than usual" — a simple outlier check against prior runs in `history.json` would flag a regression automatically instead of requiring someone to eyeball the dashboard's line chart. The same idea applies to the cost data this revision adds: Cost Explorer's own forecast API can project the next few days of spend from the trend already being polled daily, which is a cheap way to catch a real failure mode of this design — a `destroy.yml` run that silently didn't tear something down — as a forecast that diverges from the bounded, sawtooth pattern the 2-hourly teardown should otherwise produce, rather than as a surprise on the next bill.

A production-realistic retention window. The one-day Vault Lock minimum (Section 4.6) exists to keep the testbed's teardown cycle working, not because it's the right number for a real deployment. A small business adopting this design would want something closer to the 7–35 day range common in backup guidance, which means accepting that the backup vaults can't be torn down on a short cycle and budgeting their (comparatively small) storage cost accordingly. The Terraform already supports this — `backup_vault_lock_min_retention_days` is a variable, not a hardcoded value — so this is a deployment decision rather than further implementation work.

Scoping cost to the project. `record_cost.yml` currently pulls whole-account spend from Cost Explorer, because that's what the API reports without further setup. If this AWS account were ever shared with anything else, that figure would stop being CraftHaven's cost specifically. Cost allocation tags on the tagged resources (the same `Backup=true` tags already used for backup selection could be extended, or a dedicated `Project=crafthaven` tag added) would let Cost Explorer filter to just this workload. It's also worth letting the daily poll accumulate for a few weeks before drawing any conclusion from the trend — one week of data mostly shows the shape of the destroy/redeploy cycle, not the underlying steady-state cost.

Testing messier failures. Every drill so far has been a clean, deliberate `workflow_dispatch`. Real disasters are rarely that tidy — a corrupted recovery point, a partially failed Terraform apply, or a primary region that's degraded rather than fully down would all exercise different parts of this pipeline than a manual trigger does. Some form of failure injection (for example, actually terminating the primary RDS instance rather than just running the DR workflow against it) would be a more honest test of the recovery path than repeatedly exercising the same clean trigger.

Short-lived credentials. As noted in Chapter 3 and the README, every workflow in this repo authenticates with long-lived IAM access keys stored as GitHub secrets. Moving to OpenID Connect-based short-lived credentials (GitHub's `id-token: write` permission, already present in these workflows but unused for this purpose) would remove standing credentials from the pipeline entirely — a reasonable simplification for a research testbed to have deferred, but not one a production deployment should carry forward.

5.2 Conclusion

Chapter 2 identified a gap between two extremes covered in the existing literature: disaster recovery treated conceptually or evaluated inside complex platforms like Kubernetes or hybrid cloud, with little practical evidence for what a small business could realistically run on a single cloud provider with no dedicated infrastructure staff. This dissertation built and ran an implementation aimed squarely at that gap — CraftHaven, an AWS-native environment for a fictional small e-commerce vendor, backed by automated backup, Infrastructure-as-Code recovery, and a public, version-controlled record of every result.

What running it actually showed is more modest than what building it might suggest, and Chapter 4 was deliberately careful about that distinction. One drill produced an RPO consistent with the hourly backup design, and an RTO that turned out to be a lesson in measurement methodology rather than a headline number — the kind of finding that only shows up when a system is actually operated rather than described. The clearest concrete result of this work is that Backup Protection moved from a Terraform capability to an enforced, running control (Section 4.6) without giving up the cost-bounding teardown that had been the reason it was disabled — evidence, on a small scale, that the automation-without-idle-cost trade-off this dissertation argued for in Chapter 3 extends past the recovery mechanism itself and into how the backup layer is operated day to day.

The honest summary is that this project demonstrates the pipeline works, not yet that its numbers are statistically dependable — that requires the repeated, controlled drills set out in Section 5.1. What it does show, and what Chapter 2's gap was really asking for, is that a small business with no dedicated infrastructure engineer can run something more capable than manual backup-and-restore, considerably cheaper than hot standby, entirely defined in code, and — as of this implementation — with backups that are genuinely protected against deletion rather than merely configured to be.
